## Current provider contracts and limits

### HubSpot

The adapter pins CRM calls to API version `2026-09`. Its three object operations are distinct: bare collection reads use `GET /crm/objects/2026-09/{objectType}?limit=...`; activity queries use `POST /crm/objects/2026-09/{objectType}/search`; batch record reads use `POST /crm/objects/2026-09/{objectType}/batch/read`. Association traversal uses `GET /crm/objects/2026-09/{objectType}/{id}/associations/{toObjectType}`, and portal identity uses `GET /account-info/2026-09/details`. The official [Fall 2026 developer rollup](https://developers.hubspot.com/changelog/fall-2026-spotlight) (checked 2026-10-07) lists Meetings among the APIs updated in 2026.09 and says nearly all listed API updates are version-parity releases. The official [meeting retrieval reference](https://developers.hubspot.com/docs/api-reference/latest/crm/activities/meetings/get-meetings), checked 2026-10-07, now documents the bare `GET /crm/objects/2026-09/meetings` collection endpoint and its pagination, properties, and associations query parameters. That verifies the 2026-09 meeting collection GET only. It does not document the adapter's separate meeting `POST /crm/objects/2026-09/meetings/search` or `POST /crm/objects/2026-09/meetings/batch/read` request/response shapes; verify those exact operations with an isolated portal. The official [2026-03 API reference overview](https://developers.hubspot.com/docs/overview?Tag=Events) documents the date-version path pattern. HubSpot's [date-based versioning announcement](https://developers.hubspot.com/changelog/introducing-date-based-api-versioning) documents the `/YYYY-MM/` scheme and release cadence.

The adapter requests these properties from `hs_timestamp` plus object-specific fields: meetings (`hs_meeting_start_time`, `hs_meeting_title`, `hs_meeting_body`, `hs_meeting_outcome`, `hubspot_owner_id`); calls (`hs_call_title`, `hs_call_body`, `hs_call_status`, `hs_call_disposition`, `hs_call_direction`, owner); emails (`hs_email_subject`, `hs_email_text`, `hs_email_direction`, `hs_email_status`, owner); communications (`hs_communication_channel_type`, `hs_communication_logged_from`, `hs_communication_body`, owner); and notes (`hs_note_body`, owner). The adapter's `/search` POST uses a `hs_timestamp` GTE/LT filter, a stable timestamp sort, a maximum page size of 200, and HubSpot's returned `after` cursor. `/batch/read` POST requests are grouped at no more than 100 IDs. These are implementation limits; the exact 2026-09 meeting `/search` and `/batch/read` request/response behavior remains to be confirmed in an isolated portal. Association traversal requests contact/company IDs and follows returned cursors.

Email eligibility is deliberately narrow: only CRM `emails` objects whose `hs_email_direction` is exactly `EMAIL` are eligible. Other or absent directions are excluded. HubSpot's older official [email-engagement scope notice](https://developers.hubspot.com/changelog/announcement-new-scope-required-to-get-the-content-of-email-engagements) says email engagement content can be redacted without `sales-email-read` for app/OAuth access; this does not establish the current behavior for every private-app/service-key setup. Verify the token's exact scopes and a redacted direct-email fixture in the pilot portal before enabling email copies. The current docs reviewed here do not establish the `hs_email_direction` value taxonomy or the exact 2026-09 email search response shape.

Do not treat the CRM communications object as proof that SMS is readable: verify the tenant's communications channels, properties, and scopes separately. HubSpot's 2026-09 write-validation change also applies admin-configured required-field and association rules to CRM API writes; see its [official notice](https://developers.hubspot.com/changelog/crm-api-write-validation-enforcement). The normal H2A sync path reads from HubSpot without writing there; explicitly approved in-app review resolutions can perform the narrowly scoped HubSpot writes described below.

### Albi

The adapter uses the Guardian Albi Wrapper at `https://albi.guardianrestoration.com`. It sends the saved company-scoped credential only in `X-API-Key`. `GET /v1/companies` must return exactly one authorized company before the adapter makes any company-scoped request. For Allied, confirm that the response is **Allied Restoration Services Inc**, company ID `1319`. The ID is discovered from the key; administrators do not enter it and browser requests cannot override it. Zero, multiple, or malformed company results fail closed.

The wrapper [OpenAPI document](https://albi.guardianrestoration.com/openapi.json) defines these H2A operations and required scopes:

| Operation | Scope |
|---|---|
| `GET /v1/companies/{companyId}/contacts` | `contacts:list` |
| `POST /v1/companies/{companyId}/contacts` | `contacts:create` |
| `GET /v1/companies/{companyId}/organizations` | `organizations:list` |
| `POST /v1/companies/{companyId}/organizations` | `organizations:create` |
| `GET /v1/companies/{companyId}/activities` | `activities:list` |
| `POST /v1/companies/{companyId}/activities` | `activities:create` |
| `GET /v1/companies/{companyId}/options/relationship-types` | `options.relationship-types:list` |
| `GET /v1/companies/{companyId}/options/referral-sources` | `options.referral-sources:list` |
| `GET /v1/companies/{companyId}/options/relationship-statuses` | `options.relationship-statuses:list` |
| `GET /v1/companies/{companyId}/options/activity-types` | `options.activity-types:list` |

Relationship types supply the contact-type and organization-type choices used in create payloads. Contact creation accepts `organizationId`, so H2A associates a new contact with its resolved organization in that request. The activity request uses `typeId`, `date`, `notes`, a contact or organization target, and the existing HubSpot source marker. Read-after-write marker visibility still must be proven in the isolated pilot tenant.

The connection check is read-only. It validates authentication, exact-one-company access, list operations, and required option lists. Create operations appear as **Verified when first used** because proving their scopes during setup would create real records. Existing-record field changes and reassociations appear as **Handled through Conflicts** because the wrapper exposes no general update or standalone association contract. Neither informational state blocks activation. A wrapper `401` means the key is invalid or revoked. A `403` means the authenticated key lacks the exact scope displayed by the application.

## Guarded smoke script

Credential-free deterministic check (always selects local fixtures, even if provider environment variables are configured):

```sh
npm run test:h2a:e2e
```

Invoking `node scripts/test-h2a-end-to-end.mjs` without flags also selects fixtures. Provider access requires the explicit `--provider-smoke` flag; `--self-test` takes precedence when both flags are supplied. The default path performs zero network requests and zero provider mutations.

The self-test also executes the production sample-review and run handlers, authorization, projections, repository queries, matching evaluator, and recheck service against in-memory storage and provider fixtures. It rejects member list/detail requests, accepts company admins, strips injected credentials/activity content/provider errors, proves recheck cannot access provider or sync write capabilities, preserves original sample totals, rejects full from an individually cleared old sample, and accepts full only after a fresh completed sample with zero captured rows. Its diagnostic RPC fixture does not prove database transactions, grants, RLS, or concurrency.

The resolution fixture executes the production planner and resolution service: one exact HubSpot field PATCH occurs after durable intent, lease, and execution-context storage, followed by read-after-write verification. A timeout after the fixture applies that PATCH is reconciled by reads, and rerunning the intent makes no repeated write. It also checks manual Albi field tasks and fixed contact/organization deep links without an Albi update, plus a reviewed mapping and an already-associated organization choice without provider mutation or live dispatch. These are fixture contracts only. Actual HubSpot pilot writes use the application's durable resolution flow; this script has no standalone live HubSpot resolution-write driver.

Provider read-only mode requires `H2A_TEST_HUBSPOT_TOKEN` and `H2A_TEST_ALBI_KEY`. It performs authenticated reads only: HubSpot portal identity, seven-day activity searches for all five supported object types, up to five sample association traversals per type, and Albi option/contact/organization/activity reads. It reports only capability names, counts, safe short ID suffixes, and a planned prefix; it never prints credentials, headers, raw provider bodies, activity bodies, or full provider IDs. Without either credential, it exits successfully and lists only the missing variable names.

After separate provider-access approval, select that path with `node scripts/test-h2a-end-to-end.mjs --provider-smoke`. Leave both write flags unset for reads only.

The write path requires all of the following:

- Both test credentials above, connected to an explicitly isolated pilot portal and Albi sandbox/test tenant.
- `H2A_ALLOW_SANDBOX_WRITES=true`.
- `H2A_ALLOW_HUBSPOT_REVIEW_WRITES=true` (exact lowercase value) as the additional review-write acknowledgement. Either write flag requests guarded mode: all acknowledgements must pass before constructing provider clients or making any provider request. This acknowledgement does not enable application rollout.
- `H2A_SANDBOX_ISOLATION_ACK=I_CONFIRM_THIS_IS_AN_ISOLATED_ALBI_SANDBOX` after the operator has checked the Albi tenant and credentials.
- `H2A_ALBI_ACTIVITY_CONTRACT_ACK=I_VERIFIED_ALBI_ACTIVITY_MARKER_READBACK` only after the operator has verified `source`/`sourceId` and the exact `Source: HubSpot meeting <id>` marker readback in that sandbox.
- A stable `H2A_SMOKE_RUN_ID` (4–48 letters, digits, underscores, or hyphens). Reuse the same value for retry verification. Never set provider URL overrides; adapters use fixed official hosts.
- A wrapper key with `contacts:create`, `organizations:create`, and `activities:create`, plus the six required list/option scopes used by readback. The connection check cannot prove create scopes without writing, so the smoke's first guarded create is their runtime verification. Existing-record updates and reassociations remain Conflict-review operations and do not block live activation.

When all gates are satisfied, it creates or reuses one uniquely prefixed organization and contact, associating the contact with the organization in the create request, then uses the production `buildAlbiActivity`, `reserveDelivery`, `completeDelivery`, and reconciliation code for one marked activity. It reruns the delivery claim and verifies exactly one matching activity marker. IDs are printed only as four-character suffixes. It never deletes records; operators manually remove the `H2A-SMOKE-<run id>` records after review. Credential-free self-test invokes this same smoke orchestration with fake adapters and checks read-only planning, create-plus-rerun exactly-once behavior, and that every missing write acknowledgement results in zero transport calls. It is a local orchestration test, not provider evidence.

As of this runbook revision, the test credentials and acknowledgements are absent, and the public Albi activity/source-marker contract is not verified. The script must stop before provider writes until all gates pass. The implementation's ephemeral smoke delivery store proves only the in-script retry path; it does not replace the durable Supabase delivery RPC race test below.

5. Configure `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `INTERNAL_CRON_SECRET` only in the server/function environment. Keep the service-role key server-side. For local function checks, use non-production values.

## Reviewing a day's queue

Sample review and Conflicts share one review workspace. Work the buckets left to right; each record shows what HubSpot and Albi disagree on and one suggested action.

- **Quick wins**: one clear suggestion (a single strong match to link, or a new record that is ready to create). Accept it, or open the record to change your mind.
- **Needs decision**: several candidates, field differences, an organization association, or a new record that still needs a choice.
- **Blocked**: something outside the app stops the action, such as a missing Albi Referrer type or salesperson, or a HubSpot record merged into another. The record names the reason.
- **Albi to-do**: you chose HubSpot values for fields that only Albi can change. The to-do view lists each Albi edit with copy buttons and a direct link. Make the edits in Albi, then tick the records and choose **Recheck done**.
- **Done**: linked, created, skipped or cleared records, kept for the audit trail.

Keys (ignored while typing in a field, on key repeat, and with Meta, Ctrl or Alt held): `j`/`k` next/previous record, `Enter` or `a` accept the suggestion, `1`-`9` pick a candidate, `l` link, `n` create, `s` skip (live review only), `r` recheck, `x` tick for bulk, `t` open the Albi to-do, `u` undo, `?` help.

- Every create has its own **Referral source** dropdown, filled from Albi. It starts at the record's default when there is one (a contact uses its organization's referral source in Albi, otherwise the HubSpot owner's default from Settings > Sales Team) and says where it came from; otherwise it starts blank and **Create** stays disabled until a source is chosen. Nothing is remembered between records. Creating an organization and its contact uses one choice for both. New Albi records are always Type Referrer, Status Active, with the salesperson matched to the HubSpot owner.
- Most actions apply after a 5-second undo window; press `u` or choose Undo to cancel. Leaving the page or switching company sends anything pending immediately. Force-create despite candidates, many-to-one approval, any HubSpot field write, adding a HubSpot association, and every bulk action ask for confirmation first.
- In **Quick wins**, **Link all exact matches** links the records that have a single exact match and **Recheck selected** rechecks the ticked ones. Bulk link never creates records, never writes fields, and skips a match already linked to another HubSpot record, with the reason shown.
- **Create selected** queues creates for the ticked no-match records (or every one in Quick wins when none are ticked, up to 50) in the **Outbox**, and the records move there at once, so you can keep working. Its dialog starts on **Each record's default**: each record uses the referral source it would default to on its own; **Records without a default** either skips them (they fail in the Outbox with "no default referral source", and **Back to review** returns them to choose one) or uses a chosen fallback. Picking a single source instead applies it to all. Each queued create runs the record's own create checks before it is sent; one that is not ready fails in the Outbox with the reason. Recheck the created records afterwards to clear them. (The earlier background create batch, `supabase/h2a-review-create-batches.sql`, is no longer used by the page; its endpoint still supplies Albi's referral sources.)

The record moves to the **Outbox** tab at once and nothing in the page waits on Albi. One background worker per company sends one action every 1.5 seconds; when Albi answers 429 (busy) the action goes back in line and the worker pauses 30 seconds, doubling up to 10 minutes. After 8 busy refusals, or any other failure, the action stays in the Outbox with its reason, with **Retry** (back in line) and **Back to review** (cancelled, record returned to its tab). The hourly job starts a worker for any outbox left waiting. Every action is the same audited, idempotent resolution as before, so a worker that stops mid-send is safely resent. Queued creates in one worker run share one read of Albi's contact (or organization) list, grown with each record created and read again after 5 minutes, so each create is checked without re-reading Albi and two HubSpot records for one person are not both created.

## Manual recovery and disablement

- A failed or paused run is resumed through the existing admin Run now / retry path after reviewing its sanitized status and item outcomes. Do not reset cursors or delete delivery rows to force a retry.
- For a wrapper `401`, replace the invalid or revoked Guardian key and rerun the connection check and mapping confirmation. For a read/option `403`, add the named scope and rerun the connection check. For a first-use create `403`, add the named create scope and rerun the unresolved work; never advance a checkpoint manually.
- Delivery states `delivered` and `reconciled` are terminal. A stale `reserved` or due retryable `failed` claim must reconcile against Albi before another create. If Albi activity listing or exact marker matching fails, stop retries and investigate the tenant manually.
- Conflict resolution is idempotent and schedules a targeted resume. If it reports saved-but-resume-pending, use the authorized retry path; do not create a duplicate mapping manually.
- Disable the company in Settings before rotating credentials, changing mappings, or investigating. Disabling prevents new scheduled work but does not roll back records already created in Albi.
- Check `H2A` run alert delivery and tenant-specific configured recipients after failures. Notifications omit provider errors and activity contents; troubleshoot from sanitized run status and provider dashboards.
- Retained sync runs, delivery records, and live-conflict records have no automatic cleanup. Preserve their audit and delivery state unless an approved retention procedure says otherwise. After a review-capable sample completes and is confirmed as the current set, automatic cleanup prunes superseded review rows and cascading review events only for explicitly selected completed or cancelled version-one bounded samples in that company. Queued, running, paused, partially failed, and failed review sets remain available for resume; cleanup failures leave older details inaccessible through the current-set API and retryable for maintenance.
